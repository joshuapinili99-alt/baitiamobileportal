V25 RESPONSIVE MOBILE APP NAVIGATION
- Phones and compact screens up to 1023px use an app-style left navigation drawer; coarse-pointer tablets up to 1366px also use the drawer so iPad-class devices keep the app navigation in portrait and landscape where appropriate.
- A 44px touch-friendly menu button in the fixed app header opens and closes the drawer. Tapping the backdrop, the close button, a navigation item, or Escape closes it.

- Desktop/fine-pointer layouts retain the existing full navigation, while touch-first tablet layouts use the app drawer.
- Safe-area handling covers iPhone notch/Dynamic Island/home-indicator regions, while tablet and landscape breakpoints keep controls reachable without overlap.
- Main content, notification panels, chat workspaces, and fixed UI now anchor to the compact app header rather than reserving space for the old mobile navigation grid.
- Added a static web-app manifest and 192px/512px app icons for more reliable Add to Home Screen / standalone PWA behavior on supported Android, iPhone, iPad, and desktop browsers.
- Existing Firebase data structures, roles, notifications, messaging, groups, Community, Events, Q&A, Links, and Connect & Contribute logic are retained.

V24 PREVIOUS RELEASE
V24 TEAM APPLICATION ALERTS & COMPLETE LEADER PICKER
- Every Approval Leader locked to a Team by the Main Admin can now review that Team's pending applications inside Connect & Contribute > Team Approvals. Approval authority is Team-based rather than limited to only the applicant's selected contact.
- When a Team has multiple locked leaders, the applicant may still choose one primary Approval Leader contact for messaging, but every locked Team leader can see and approve/decline the pending application.
- Connect & Contribute notification badges and portal/browser notifications now recognize Team assignments, so all locked Team leaders are notified when a new application arrives for their Team.
- When one Team leader approves or declines an application, the pending item disappears from the other Team leaders' pending queues through the existing live Firestore listeners.
- New applications store the Team leader snapshot in teamLeaderIds for routing/audit continuity. Changing locked leaders synchronizes pending application routing metadata.
- Main Admin > Approval Leader Management now lists every registered account supplied by the portal users collection, including Main Admin, Co-Admins, regular users, and accounts not yet approved.
- Existing Approval Leaders remain visible in the picker and are marked as already appointed instead of disappearing.
- Added a searchable account field for Approval Leader selection by name, login ID, email, role, or status, plus a shown/total account count.
- Accounts that are not yet approved may be appointed for future use, but they cannot sign in to use the approval queue until their portal account itself is approved.
- Only the Main Admin can appoint/remove Approval Leaders or change Team-to-leader locks. Co-Admins keep their existing application review permissions but cannot edit leader assignments.


V23 CONNECT & CONTRIBUTE - TEAM-LOCKED APPROVAL LEADERS
- Main Admin can now lock one or more appointed Approval Leaders to each specific Team inside Connect & Contribute > Admin > Team Management.
- Co-Admins can see the locked leader assignment but have no UI control to add, remove, or change the Team leader mapping. Team name/description management remains available to Co-Admins.
- Users see Team Approval Contacts grouped by Team and can message only the Approval Leaders locked to the relevant Team.
- New team applications can select only leaders locked to that Team. If exactly one leader is locked, routing is automatic. If several are locked, the user selects from that Team-only list.
- If no leader is locked to a Team, users can still apply and the application remains reviewable by Main Admin and Co-Admins.
- Appointed Approval Leaders see and can review only pending applications routed to them. Unrelated or general-queue applications are no longer exposed to other Leaders.
- Changing a Team's locked leader list automatically reroutes pending applications whose prior leader is no longer eligible.
- Removing an Approval Leader also removes that user from every Team lock and reroutes pending assigned applications to another locked Team leader when available, otherwise to the admin approval queue.
- New Teams are created with an explicit empty approvalLeaderIds lock list so leader routing starts in a controlled state.
- Team leader lock metadata is stored on contributeTeams using approvalLeaderIds, approvalLeadersLocked, approvalLeadersUpdatedAt, approvalLeadersUpdatedBy, and approvalLeadersUpdatedByName.

V18 MAIN ADMIN DIRECT BROADCAST
- Added Main Admin > Direct Broadcast.
- The Main Admin writes one message and the portal delivers it as a separate private Direct Chat message to each approved BAITIA user and Co-Admin.
- It is not a group chat. Recipients cannot see the other recipients and can reply privately to the Main Admin.
- Broadcast delivery is chunked to stay safely below Firestore batch write limits.
- Creator/maintenance account and the sending Main Admin account are excluded from recipients.
- No new Firestore collection is used. Direct Broadcast writes to the existing chats/{chatId} and chats/{chatId}/messages collections.

DEPLOYMENT
1. Upload BAITIA_V24_Netlify_Ready.zip directly to Netlify, or deploy the extracted folder with index.html at the site root.
2. Keep service-worker.js and _headers at the same root level as index.html.
3. If using a new Netlify domain, add that exact domain in Firebase Authentication > Settings > Authorized domains.
4. After deployment, perform one hard refresh on test devices so the latest service worker takes control.

FIREBASE / SECURITY RULES
- Direct Broadcast requires the Main Admin to be allowed to create/update chat metadata and create messages in conversations where the Main Admin is a participant.
- Connect & Contribute notification listeners read contributeApplications, contributeLogs, and the current user's contributeLeaders permission record. Production rules must permit intended users/reviewers to read the records required by their role.
- The new contributeLeaders collection should be readable by approved portal users, writable only by the Main Admin, and should use the appointed user id as the document id. Firestore rules must enforce this because frontend UI checks alone are not a security boundary.
- For V23 Team leader locks, Firestore rules should also prevent Co-Admins and regular users from changing approvalLeaderIds or approvalLeadersLocked on contributeTeams. The frontend hides these controls from Co-Admins, but server-side rules are required if this restriction must be tamper-resistant against direct Firestore/API writes.
- Announcement comments continue to use announcements/{announcementId}/comments/{commentId}.
- No Firestore rules file was supplied in the website package, so production rule changes cannot be bundled into this Netlify ZIP.

NOTIFICATION LIMITATION
- In-site alerts and background-tab browser notifications use the included frontend/service worker implementation.
- True remote push when the browser is fully closed requires Firebase Cloud Messaging (or another push backend) and server-side push delivery. That infrastructure is not present in this frontend-only package.
